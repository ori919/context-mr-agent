### Why this matters
This MR introduces self-service password recovery, changing the authentication flow to
allow users to reset their credentials without admin intervention. It touches the token
generation pipeline, the email delivery path, and the user settings UI — three areas that
are tightly coupled to session management and account security.

### Affected areas
- Auth middleware (`src/middleware/auth.ts`) — token validation path now includes recovery token type
- Email delivery service (`src/services/email-service.ts`) — new template registration
- User settings page (`src/pages/settings/index.tsx`) — new recovery flow entry point
- Session management (`src/services/session-service.ts`) — sessions are invalidated after reset
- Rate limiting (`src/middleware/rate-limiter.ts`) — reset endpoint needs its own rate limit bucket

### Hidden assumptions
- Recovery tokens are enforced as single-use server-side, but the client does not prevent double-submission — race conditions are possible under concurrent requests
- The email provider may retry delivery, potentially sending multiple reset links for a single request
- The UI assumes the user is logged out after a successful reset, but the session invalidation is asynchronous — a brief window exists where the old session remains valid
- The migration is irreversible (`DROP TABLE` in down migration deletes all recovery token history)
- No CAPTCHA or secondary verification is applied to the reset endpoint — relies solely on rate limiting

### Risk level
**High**
Changes span authentication, token generation, database schema, and session lifecycle.
A defect here could lock users out or create a session hijacking vector.
